
## WorkTable schema changes — check before every deploy

> **A WorkTable schema change is a deployment event, not just a code change.**

This repo has **7 `worktable!` definitions**, **6 with `persist: true`**
(those hold on-disk data). If their schema moves, upgrading versions and
deploying becomes significantly more complicated, and the change **must** ship
with a WT data migration script.

**Before any merge → deploy, verify whether the WorkTable schema changed:**

```bash
git diff <base>..HEAD -- 'src/db/**'                              # definitions
git diff <base>..HEAD -- Cargo.toml Cargo.lock | grep -i worktable # crate version
grep -rn "persist: *true" src/                                     # which tables persist
```

A schema change is: adding/removing/renaming a column, changing a column's type
or optionality, altering an index or primary key — **or bumping the `worktable`
crate version**, which can change the on-disk format with no source edit at all.
That last one is the easiest to miss.

If any of it moved on a `persist: true` table, write the migration script and
ship it with the change. Do not leave it to deploy time.

Do **not** assume a dependency upgrade leaves WorkTable alone because it looks
unrelated. See `docs/worktable-schema-and-deploy.md` for the full guidance and
the endpoint-libs 2.0 precedent (checked 2026-07-25 — clean, no migration needed).
